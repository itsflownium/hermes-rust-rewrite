# Discord stock plugin implementation spec

Discord is Mercury's first stock messaging plugin after the shared contract expansion. An operator can configure a bot in a profile, use it for agent work in Discord, and recover the same sessions and deliveries after restarting Mercury. Complete Discord's acceptance gate before starting Telegram. [Backend parity plan](../../BACKEND_PARITY_PLAN.md) · [Shared stock-plugin requirements](ADAPTER_CONTRACT.md#shared-requirements-for-stock-plugins) · [Telegram implementation spec](TELEGRAM_ADAPTER_SPEC.md)

The behavior baseline is the bundled Discord platform in Hermes v0.23.4. This includes Discord bot DMs, guild text and announcement channels, threads and forum posts, native commands, supported media, and Discord voice channels. Discord's current Gateway, REST, interaction, and voice APIs define the wire behavior. [Hermes Discord platform](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/discord/plugin.yaml) · [Hermes Discord guide](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/discord.md) · [Hermes voice guide](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/features/voice-mode.md)

## Target architecture

Mercury's profile owner already passes the core polling and push conformance suite. The shared implementation gate supplies profile-managed setup, commands, prepared intake, and delivery extensions before Discord starts. Discord uses that contract for its first production transport. Implement Discord in the `hermes-discord-plugin` workspace crate at `crates/plugins/discord`. The gateway owns the shared Rust adapter contract. The bundled gateway registers Discord at startup, and the profile owner configures its connections through the adapter registry. Reuse `reqwest` and `tokio-tungstenite` for Discord REST v10 and Gateway v10 so the adapter can resume from the host's committed sequence. Use Songbird's standalone driver with receive support for Discord voice transport. The Discord module composes these clients under the host's connection lease. [Gateway startup](src/lib.rs) · [Adapter interface](src/messaging/types.rs) · [Owner startup](src/owner/cli.rs) · [Songbird driver](https://github.com/serenity-rs/songbird/blob/v0.6.1/README.md)

| Owner | Responsibility |
| --- | --- |
| Discord adapter | Verify the bot, run the Gateway and voice connections, maintain Discord guild, thread, permission and membership evidence, normalize Discord events, render operations, and return classified platform evidence. |
| Profile messaging host | Own configuration and secret references, account leases, access and route selection, ingress receipts, checkpoints, route provisioning, and ordered outbox operations. Authorize typed operations at their boundaries. |
| Native session authority | Own turns, queue edits and cancellation, steering and redirects, command effects, approvals, clarification requests, and committed outcomes. |
| Engine and audio services | Run the provider and tools with the selected profile settings. Transcribe authorized clips, synthesize speech, and stage files through scoped attachment services. |

Use the stock requirements in the shared contract for host capabilities. The Discord module consumes those operations through the scoped host API. Persist message, command, and delivery identities in the owning profile's `mercury.db` through the existing host store. Discord-only metadata can live in a namespaced record in that database, scoped to the verified account. Keep prepared plans effect-free. Network mutations that create durable user-visible effects are host-issued operations with a stable identity, a recorded attempt and classified evidence. [Messaging runtime](src/messaging/runtime.rs) · [Messaging store](src/messaging/store.rs) · [Native turn authority](src/authority.rs)

## Profile configuration and access

- Register the Discord settings shape with the shared profile configuration. Its entry carries a connection name, enabled state, bot secret reference, verified application and account binding, guild, channel and thread rules, user and role grants, command and media policy, recovery limits, and a default delivery target. Expose create, verify, rotate, update, and disable through the private native owner. Persist only a secret reference in adapter settings. Use Mercury's existing credential service for sealed secrets and allow a profile-bound deployment secret reference for unattended hosts. Status includes connection, verified bot identity, readiness, missing permissions or intents, and receipt identifiers. Credentials, interaction tokens, signed media URLs, and message contents stay out of status and diagnostics. [Credential storage](../engine/src/secret.rs) · [Native profile owner](src/owner/mod.rs)
- Verify the authenticated bot user and its application with read-only REST before acquiring the installation-wide account lease. Identify on the socket, register commands, and start delivery only under that lease. Match the identity in READY to the verified account. Rotating a token for that account preserves routes and pending work. Configuring a different account creates a new identity and leaves earlier work bound to its original account. Classify invalid credentials or privileged intents as configuration failures that an operator can repair. Report socket readiness separately from REST health. A closed socket or missed heartbeat acknowledgement triggers recovery. A configurable dispatch-silence limit detects a stalled connection that still acknowledges heartbeats. [Discord Gateway](https://docs.discord.com/developers/events/gateway) · [Discord status codes](https://docs.discord.com/developers/topics/opcodes-and-status-codes)
- Resolve permission by verified Discord snowflakes for guilds, channels, threads, users, roles, and approved bot senders. A deny or ignored channel wins. Apply exact thread or forum-post overrides before the parent rule, then guild and profile defaults. DMs can use a user grant, profile-approved pairing, an explicit open DM policy, or a role grant from one configured DM authorization guild. Guild-channel role grants are evaluated in the channel's own guild. An explicit open rule can admit users on a configured guild surface. An eligible user's command and operator grants are evaluated independently of chat admission. Use Discord membership events to expire role evidence and a bounded scoped REST lookup when a decision requires fresh evidence. Fail closed for missing evidence on a restricted route. Remove access before a queued claim, control, or delivery effect even if an earlier intake was accepted. [Hermes guild-scoped role checks](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/discord/adapter.py#L3859) · [Discord permissions](https://docs.discord.com/developers/topics/permissions)
- Authorize guild text on a bot mention by default. Support explicitly mention-free channels, the participated-thread exemption, and a per-thread mention override. Suppress guild messages addressed to other users under the configured mention rule. Omit the bot's own messages and keep other bots and webhooks disabled by default. A trusted handoff requires an allowed sender and a literal mention of this bot. A bounded, same-sender, same-channel or thread burst can continue that admitted handoff. Coalescing preserves the identities and order of all contributing events. [Hermes Discord live gates](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/discord/adapter_live_gates.py) · [Hermes Discord admission](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/discord/adapter.py#L1632)
- Request only the Gateway intents needed by the selected capabilities. Verify Message Content for configured guild behavior, member access for role policy, and Voice States for live voice. Derive the bot invite scopes and permissions from enabled capabilities. Support profile-configured proxy transport for HTTP and Gateway WebSocket connections. Live voice setup checks its separate UDP connectivity. [Discord Gateway intents](https://docs.discord.com/developers/events/gateway#gateway-intents) · [Discord application authorization](https://docs.discord.com/developers/interactions/application-commands#authorizing-your-application) · [Discord voice transport](https://docs.discord.com/developers/topics/voice-connections)

Set `delivery.typing` or `delivery.reactions` to enable feedback for native turns. Reactions use the verified source message and an ambiguous reaction leaves the reply eligible for delivery. Set `media.spoken_replies` to `off`, `voice_notes`, or `always`. The default `voice_notes` mode uses authenticated Discord voice-message intake to select spoken replies. The `always` mode applies to replies with a native channel source. Where the profile enables spoken replies, `/voice on`, `/voice off`, and `/voice tts` set the mode for the current room or thread, and `/voice status` reads it privately. Spoken replies use the profile speech service.

## Routes, native work, and recovery

**Route identity.** A DM uses its channel ID. A guild route uses its channel ID and an optional thread or forum-post ID, with the guild and parent validated from Discord metadata. The host combines those values with the verified account and owning profile. Guild conversations default to per-user sessions. A room policy can opt into a shared session with the corresponding shared turn order. Effective model, channel prompt, skills, tools, and approval settings resolve from the profile through the exact room override, then become the settings for that claim. The channel prompt is separate from the user's text. [Hermes Discord session model](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/discord.md#session-model-in-discord) · [Channel prompt and skill resolution](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/discord/adapter.py#L4658)

**Thread creation.** For auto-threading, durably reserve the accepted event and the intended route before provisioning. Discord's thread-from-message operation gives the thread the starter message ID. Lease creation through the host and confirm the exact thread and parent before the native claim. A known refusal can use an explicitly configured inline fallback, with the selected destination persisted once. An uncertain result holds the provisioning operation until verified. Support manual thread creation and optional bot-owned thread title and pin updates. In an existing forum post, send into its thread. A proactive send to a forum root creates a post with a starter message and records both returned IDs before sending further parts. An uncertain forum create stays fenced until platform evidence or owner resolution. [Discord channel and thread operations](https://docs.discord.com/developers/resources/channel#start-thread-from-message) · [Hermes thread title behavior](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/discord/adapter_thread_titles.py) · [Hermes forum delivery](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/discord/adapter.py#L3088)

Enable `delivery.rename_auto_threads` to derive a short title from the first committed reply in an auto-created thread. Mercury checks the exact guild, parent, bot owner and original title before issuing the edit. Enable `delivery.pin_first_thread_message` to pin the first confirmed bot reply in an auto-created thread or the bot's starter in a manually named thread. Pinning needs Discord's `PIN_MESSAGES` permission. Both options default to off. The original reply remains delivered while optional updates are pending. On a lost response or restart, verify the exact existing state before recording success. A confirmed update stays settled after moderator changes. [Discord Modify Channel](https://docs.discord.com/developers/resources/channel#modify-channel) · [Discord Pin Message](https://docs.discord.com/developers/resources/message#pin-message)

**Live intake.** Give message creates an identity based on the message ID and interactions a distinct identity based on the interaction ID. Keep immutable content and attachment identities separate from live role evidence, expiring media URLs and derived context. A replay with changed authorization evidence still reads the original intake decision. A conflicting reuse of the immutable identity is visible as a conflict. Gateway HELLO, heartbeat requests, heartbeat acknowledgements, reconnect opcodes and READY or RESUMED are handled by the Discord connection. Use the latest received sequence for heartbeat and the last committed sequence for RESUME, with Discord's session ID and validated resume URL in the host checkpoint. Unhandled dispatches only advance the committed prefix after a durable disposition. Drain committed work on a planned reconnect and preserve the session's RESUME eligibility. An explicit disable closes the account session and releases its lease. Respect Discord session-start limits on fresh Identify. [Discord connection lifecycle](https://docs.discord.com/developers/events/gateway#connection-lifecycle) · [Mercury checkpoint gate](src/messaging/runtime.rs)

**Recovery and history.** If Discord declines RESUME, report an intake gap and open a fresh session. The optional missed-message scan uses configured channels and reachable threads, a time window, a scan and dispatch budget, and a durable cursor per surface. Feed the recovered message IDs through the live admission path in source order while buffering new arrivals for the affected destination. An already handled message or uncertain execution remains represented by its prior receipt. Keep unrecoverable interactions and incomplete scans visible in gap status. Separately support optional, bounded context from recent authorized scrollback of the triggering channel or thread. Attach it as attributed context to the turn. It never creates an admission on its own. [Hermes Discord recovery](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/discord/recovery.py) · [Hermes history and missed-message backfill](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/discord.md#discordhistory_backfill)

**Deferred preparation.** Use shared deferred intake for accepted events that await scoped media staging or route provisioning. Persist their immutable references, disposition, and sequence before advancing the checkpoint. Preserve the order of ordinary work in each route until preparation succeeds or records a refusal. The host may commit an interaction in the same durable stream without waiting for an earlier attachment download to finish. Only a completed, reauthorized preparation can become a native turn. Explicit queued edits use the native receipt as their target. Normal message edits, deletions, reactions, and thread lifecycle events use typed event metadata when a supported native subscriber is configured.

## Commands and interactions

Build Discord application commands from the shared native command and skill descriptors, each with a canonical command ID, permission, typed arguments, and visibility. Register only supported commands, with stable names and a deterministic budget for Discord's command limits. Support the default safe incremental sync and an explicit registration-off mode. Allow a test guild for immediate fixture and live runs, and use `contexts`, `integration_types`, and `default_member_permissions` for the supported DM and guild surfaces. Enforce command and administrator policy again at invocation. [Hermes command sync](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/discord/adapter_command_sync.py) · [Discord application commands](https://docs.discord.com/developers/interactions/application-commands)

| Surface | Native behavior to connect |
| --- | --- |
| Help, identity, status and history (`/help`, `/whoami`, `/status`, `/history`) | Return only the authorized scope's operations and data. Render private results as ephemeral responses where applicable. |
| Conversation and background work (`/reset`, `/bg`, `/stop`, and registered skills) | Submit chat and skills through native admission. Route new/reset, queue editing, steering, redirecting, and stop to native controls. Route background work to durable native execution and its original Discord destination. |
| Model selection (`/model`) | Provide direct model selection and the provider/model picker from the profile's supported choices. Bind selections to their actor and route and fence changed settings. |
| Approval and clarification | Render separate prompt content and controls for each native request. Support native approval decisions at the granted scope, including once, session, and persistent approval where the owner policy permits them. Accept choice and free-text clarification. Bind all responses to the exact actor or allowed operator, route, request and execution generation. Retire controls on settlement, cancellation, or expiry. |
| Channel and voice commands (`/sethome`, `/thread`, `/voice`) | Support home target selection, thread creation, voice reply mode, and joining or leaving a voice channel through scoped native operations. |

Discord returns `/history` privately and limits it to recent delivered turns from the invoking route. A `/bg` invocation queues a separate native job with the requester and destination pinned. A `/thread` invocation creates one quiet starter marker in the approved guild channel, provisions its thread from that exact message, and sends any supplied starter text into the confirmed thread.

Discord requires the initial HTTP interaction response within three seconds. Commit the authenticated interaction or its refusal through the host first. Give callbacks a dedicated bounded path ahead of model runs, file downloads, outbox ordering, and command sync. An accepted callback can defer the result. A known failed intake gets a private unavailable response while the token is valid. An uncertain commit keeps its interaction identity until the host can read the disposition. Record expiry when Discord has closed the callback window. A repeated interaction returns the saved disposition and uses Discord's single callback identity. Read the shared control receipt to render applied, forbidden, stale, or expired outcomes. The interaction token is short-lived and kept out of durable session and delivery data. If the callback expires, an authorized channel-visible conversational result can still use the ordinary outbox. Private command results remain private and surface expiry to the operator. [Discord interaction deadlines](https://docs.discord.com/developers/interactions/receiving-and-responding#responding-to-an-interaction) · [Hermes approval view](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/discord/adapter_exec_approval_view.py)

A component carries a short host-issued reference to the request and choice. Verify the Discord application, message, actor, route, current permissions, and expiration before resolving it. Open-ended clarification can accept the authorized actor's next text in the same route or a modal bound to the request. After restart the native pending request or its final disposition determines what that interaction can do. Advertise the approval grants supported by the native authority and the current Discord policy.

## Outbound delivery, media, and voice

**Rendering and rate limits.** Prepare ordered parts within Discord's 2,000-character message limit and applicable upload limits. Preserve Unicode and Markdown code fences across splits. Set reply references by configured mode and explicit allowed mentions on every create and edit, including follow-ups. Keep everyone and role pings disabled by default. Provide bounded typing and reaction feedback and coalesced progress or streamed edits to the bot's own confirmed message. The final output comes from the committed turn. Export replies requiring more than eight parts as complete Markdown when uploads are supported. Persist a fallback to complete ordered text after a definite upload refusal. Retire superseded previews only after the replacement is confirmed. [Discord message resource](https://docs.discord.com/developers/resources/message) · [Hermes long reply and formatting behavior](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/discord.md#long-replies)

Persist each part and attempt under the existing delivery lease. A Discord 429 supplies non-acceptance and a retry deadline. Store the cooldown for the verified bot globally or for the REST bucket and major-route parameters Discord reports. Keep unrelated destinations eligible during a scoped cooldown. A definitive permission or destination failure is recorded against that operation. For a normal message create, derive a stable Discord nonce from the delivery and part and use `enforce_nonce`. Resolve a lost response only with positive evidence for the same account and destination, such as an authenticated create dispatch with the exact nonce or a known message ID and verified provenance. Discord's nonce deduplication window is finite. Unknown acceptance waits for reconciliation or the operator. [Discord rate limits](https://docs.discord.com/developers/topics/rate-limits) · [Discord message creation](https://docs.discord.com/developers/resources/message#create-message)

**Proactive delivery.** Allow an operator to verify and select an existing channel, thread, or forum root as the profile's home or a producer-specific destination, even before a message has created a session there. Save that Discord destination under the verified account. Routines, signed webhooks and background results submit their stable producer IDs to the same outbox. Permissions and thread identity are rechecked when the effect is sent. [Mercury scheduler](src/scheduler.rs) · [Mercury signed webhooks](src/webhooks.rs) · [Hermes Discord send targets](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/discord/send_targets.py)

**Attachments.** Use shared bounded streaming capture for images, GIFs, video, documents, archives, arbitrary binary files and audio. Use a 32 MiB default inbound per-file cap with configurable finite bounds and an aggregate request budget. Resolve signed Discord attachment URLs from authenticated message metadata, validate the source and limit redirects and bytes, and stage after access is checked. Surface supported images and small text to the provider. Give other files a scoped artifact reference for tool inspection and give audio to the configured transcription service. Outbound files come from host-issued artifacts and upload to the exact approved route. Report size and permission refusals explicitly. Discord output refers to uploaded artifacts or the committed reply text. [Current attachment staging](../engine/src/attachment.rs) · [Hermes Discord media implementation](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/discord/adapter_media.py) · [Discord attachment and voice-message formats](https://docs.discord.com/developers/resources/message#attachment-object)

**Voice.** Treat Discord voice notes and live voice as required Discord acceptance cases. Voice notes use the audio attachment path and the profile STT/TTS services. Support text-only, voice-triggered spoken replies, and configured spoken replies on text. For live voice, handle the main Gateway's voice state and server update handshake under the existing account lease. Pass the resulting connection information to the standalone Songbird driver, with DAVE and receive support, using the same verified bot identity. Begin the voice work with a two-way DAVE test and release-build checks for the supported desktop and headless targets. Use the driver's Opus and DAVE stack. [Mercury transcription service](../engine/src/transcribe.rs) · [Discord voice and DAVE](https://docs.discord.com/developers/topics/voice-connections#end-to-end-encryption-dave-protocol) · [Songbird v0.6.1](https://github.com/serenity-rs/songbird/releases/tag/v0.6.1)

Join the authorized caller's voice channel and bind that voice session to the text channel or thread that requested it. Validate each speaker against current membership and profile rules. Use speaker identity, bounded utterance capture, silence detection and scoped transcription to create normal native input. Discard old captures on a binding change, leave, or permission loss. Prevent bot playback from being recaptured. Return text to the bound route and deliver synthesized playback as a scoped effect with a playback receipt. An interrupted playback is held as uncertain. Cover idle leave, bounded playback, configured spoken acknowledgements and ambient audio, and text fallback when playback is definitively unavailable. [Hermes Discord voice workflow](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/features/voice-mode.md#discord-voice-channels)

Enable `voice_fx.enabled` with live voice to play cues in the current bound call. The first native tool call can speak a short acknowledgement using profile synthesis and the configured `voice_fx.ack_phrases`. The ambient loop uses synthesized audio or an owner-configured local PCM WAV or Ogg Opus file at `voice_fx.ambient_path`. Relative paths resolve from the profile. The mixer lowers ambient volume under speech, mutes it during microphone activity, and restores it when the call is quiet. Acknowledgements end with the turn and yield to the committed spoken reply. The ambient loop runs while the connection, binding and audience remain authorized. [Hermes Discord voice mixer](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/discord/voice_mixer.py)

## Conformance and live acceptance

Drive the transport at a loopback Discord WebSocket plus a scripted REST server. Start a real profile gateway, use its private configuration surface and a deterministic model, and reopen disposable profile databases at the durable boundaries. Add voice driver and audio-provider doubles at the media seam. Retain the existing polling and push fixtures as regressions for changes to the shared interface. [Core conformance tests](src/messaging/conformance.rs) · [Native owner tests](tests/owner.rs) · [Hermes Discord contract fixtures](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/tests/e2e/core/platforms/test_discord_contract.py)

| Case | Required evidence |
| --- | --- |
| Installation and policy | Wrong token, disabled intents, inaccessible guild or thread, conflicting profile lease, matching and changed token rotation, role revocation during queue and delivery, authorized and wrong-guild DM role checks, pairing, mention rules, and trusted versus untrusted bot handoffs. |
| Session isolation and ordering | An allowed DM, two guild users in per-user and shared modes, an existing thread, duplicate auto-thread creation during reconnect, and forum create and reply. Verify exact session, actor and destination. Verify optional auto-thread title and pin updates, manual starter pinning, moderator changes, permission loss and recovery after a lost mutation response. |
| Intake and recovery | Missing heartbeat ACK, recoverable and terminal close codes, a failed intake commit, successful RESUME from committed sequence, invalid session with bounded REST recovery, replay overlap, and a visible unrecoverable gap. Verify one native claim per admitted event. |
| Commands and controls | An authorized slash skill and model change, receipt before defer, wrong actor, role, profile, thread, or generation, duplicate and expired interactions, approval, free-text and choice clarification, queue edit, steer, redirect, and stop. |
| Delivery | Multipart or edited reply after restart, bot-only message editing, long-response attachment and text fallback, safe mentions, bucket and account rate limits, missing permissions, positive evidence for a lost acknowledgment, and an unresolved send that fences only the affected destination. Include a routine and a signed webhook. |
| Media and voice | Authorized and denied attachment fetch, supported and unknown file formats, byte caps, attachment-only input, generated upload, voice-note transcription and reply, two authorized speakers in live voice, revoked or unknown speakers, old binding discard, mute/leave, DAVE reconnect, and interruption during playback. Verify the first-tool acknowledgement on the exact bound route, opt-out, cancellation, absent synthesis, ambient ducking and cleanup with local audio and driver fixtures. |

The integration gate is the Discord transport suite, the core adapter suite, and `cargo test --locked --workspace`. Confirm that the normal owner is the sole Discord runtime and that scheduled, webhook and channel replies reach the same delivery coordinator. Then use a configured test bot in a guild and a DM to exercise the matrix's user-facing paths. Record the bot's enabled scopes, intents, permissions, environment, executed cases and outcome with redacted evidence. Fixture results satisfy the transport gate. The live gate also needs real Discord interactions, a lease and restart exercise, and a real two-way voice call. Mark Discord complete only after both gates pass.

## Scope exclusions

- Other platform adapters during Discord adoption. Desktop UI work stays in the new upstream UI port.
- Hermes configuration and database compatibility, command-sync bulk compatibility, deprecated Discord command fields, old liveness aliases, and the obsolete attachment allow-any flag.
- Separately deployed Hermes Relay connectors and independently distributed Discord RPC or plugin-catalog integrations. Relay follows the gateway services roadmap. [Hermes Relay](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/relay.md)
