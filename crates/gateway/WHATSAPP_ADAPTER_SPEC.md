# WhatsApp stock plugin implementation specs

Bundle two independent stock adapters from the `hermes-whatsapp-plugin` crate. `whatsapp` connects through a linked device and `whatsapp_cloud` connects through Meta's WhatsApp Business Cloud API. Each has its own setup, verified account, connection lease, health, and capabilities. Local implementation and conformance for both adapters can proceed on the shared contract. Release availability follows Slack live acceptance, then the linked-device live gate, then the Cloud API live gate. [Shared gateway contract](ADAPTER_CONTRACT.md#shared-requirements-for-stock-plugins) · [Slack spec](SLACK_ADAPTER_SPEC.md) · [Hermes linked-device manifest](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/whatsapp/plugin.yaml) · [Hermes Cloud API manifest](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/whatsapp_cloud/plugin.yaml) · [Next adapter, Signal](SIGNAL_ADAPTER_SPEC.md)

## Behavior shared by both WhatsApp adapters

- **Authority and destinations.** The profile owner enables each plugin and supplies policy, native command and session authority, durable intake, and the outbox. Each adapter translates its own authenticated account, actor, chat, and message keys. Bind a session and record each reply's exact destination and quote anchor separately. Record verified identifier aliases in their account and namespace. Changes that cannot be verified go to the private owner for resolution. The same phone number or display name across adapters never moves a session, grant, or pending delivery. [Gateway identity and policy](ADAPTER_CONTRACT.md#identity-and-policy)
- **Message preparation.** Apply DM admission, optional DM pairing, and per-route operator and command grants. Operator-only actions include changing the home destination and widening access. Recheck grants before reading quotes, staging media, running controls, claiming work, and sending. Support authorized quoted text and media from received messages and the bot's confirmed sends, using the referenced message in the same account and chat. Keep its origin separate from the new user's text. If the authorized source has expired or is unavailable, carry that disposition with the reference. Stage bounded images, audio, video, and documents through the profile's attachment boundary. Transcribe authorized voice notes and synthesize spoken replies through the profile services. [Hermes WhatsApp behavior](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/whatsapp/adapter.py) · [Hermes Cloud API features](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/whatsapp-cloud.md#features)
- **Commands and controls.** Recognize native text commands for status, session management, model and skill selection, queue and busy-turn control, approvals, clarification, and proactive target setup where authorized. Map platform interactions to native request and generation IDs. Verify the callback's actor, audience, expiry and referenced prompt. A replay reads the existing decision. A stale or forbidden choice produces a scoped refusal and starts no turn. Keep tool progress and privileged controls within the grant for that audience. [Gateway control contract](ADAPTER_CONTRACT.md#shared-requirements-for-stock-plugins)
- **Replies and notifications.** Render supported WhatsApp emphasis, code and links, and split on safe boundaries within each transport's limits. Plan text, media preparation and publication, and eligible display effects as ordered parts. A reply can quote its confirmed source. A routine, signed webhook or background result, or authorized manual send uses the same outbox and verified target under current policy and transport eligibility. Store acceptance separately from later delivery or read evidence. Hold an uncertain effect at its exact destination until positive evidence or the owner's disposition settles it. [Gateway delivery and recovery](ADAPTER_CONTRACT.md#delivery-and-recovery)

## Linked-device adapter

**Runtime and setup.** Register `whatsapp` from `hermes-whatsapp-plugin` as the linked-device factory. Run a gateway-supervised, versioned Node.js bridge with a pinned, verified Baileys dependency. Baileys supplies the companion-device protocol. Exchange bounded, framed requests, events and receipts over a private inherited pipe. The bridge manages only protocol credentials and traffic. The native profile owner handles human setup, policy, session work, and recovery decisions. Ship the verified bridge with the supported headless distributions and surface a typed readiness reason when its runtime or assets are unavailable. [Hermes linked-device guide](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/whatsapp.md) · [Hermes bridge source](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/scripts/whatsapp-bridge/bridge.js) · [Baileys releases](https://github.com/WhiskeySockets/Baileys/releases)

- Provide a private, expiring owner setup flow for the QR scan. If WhatsApp requires a passkey, surface that state and let the owner complete it interactively in a supported browser with access to the account's passkey. Accept the verified result of that flow. Show when the required device or browser is unavailable. Keep setup artifacts and evolving auth keys out of public listeners, model context, routine logs, and status. Claim the active account lease only after the connected device proves its account. Isolate pending pairing state and persist credential mutations under the current generation in protected profile storage. [Hermes passkey pairing](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/scripts/whatsapp-bridge/PASSKEY.md)
- Expose disconnected, setup-required, reconnecting, ready, and revoked states to the owner. Resume the persisted linked session on service or bridge restart. Retire the old process and fence its events, sends, and credential writes when the generation changes. Revocation or logout requires explicit relinking. Relinking the same verified account preserves receipts and routes. A different account requires a fresh binding. Support multiple profiles with distinct accounts and refuse concurrent leases for the same account. [Hermes session persistence](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/whatsapp.md#session-persistence)

**Modes and groups.** Support personal self-chat for the paired owner and bot mode for a separate paired account. In bot mode, allow authorized DMs and opt-in groups authorized by group ID and actor policy. Default group intake to a verified mention or reply to the bot. Support explicit free-response rooms, optional scoped mention patterns and authorized voice transcription for mention matching. Apply the chosen shared or per-sender session binding, operator grants, and route overrides. Normalize phone-number JIDs and LIDs through the transport's verified association while keeping original protocol keys for quotes and sends. Treat group membership, sender identity, and DM pairing as distinct evidence. Support operator-configured human handover in bot mode where the adapter can verify owner authorship and the affected chat. [Hermes linked-device modes](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/whatsapp.md#two-modes) · [Hermes linked-device identity tests](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/tests/gateway/test_whatsapp_identity.py)

**Intake and recovery.** Scope WhatsApp message keys by verified account, chat and the sender or participant identity when required by the protocol. Submit new live messages from the bridge, including a live owner message carried in an append batch. Separate catch-up history, prompt answers, receipt events and Mercury's own outbound echoes from ordinary messages. Use the authenticated live-event and account context and durable send identities to decide where an owner-authored message can enter self-chat or invoke handover. Require sufficient evidence to distinguish that message from an echo. The `fromMe` flag alone is insufficient. An ambiguous event creates neither a turn nor a handover. If an account needs a catch-up sync, resume previously committed inputs and replayable bridge events and report any observed gap that cannot be recovered. Historical sync does not enqueue conversations. [Hermes bridge event handling](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/scripts/whatsapp-bridge/bridge.js) · [Hermes outbound message ID handling](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/scripts/whatsapp-bridge/outbound_ids.js)

Use the earliest receive point controlled by the bridge for bounded recoverable handoff. Keep a bounded handoff record under the owning profile until the host commits its disposition. Replay it across bridge reconnects and restarts. Apply backpressure and report a gap on lost intake. Baileys manages protocol acknowledgements independently of the bridge-to-host receipt. Coalesce configured short text and media bursts from the same actor and exact destination, commit all constituent keys, and close the batch before native claim. A restart or duplicate batch must never submit a constituent again. [Gateway intake and ordering](ADAPTER_CONTRACT.md#intake-ordering-and-execution-recovery)

**Native display, polls, and media.** Support optional typing and read receipts once intake and policy permit them. Provide configured progress and editable streaming previews where the linked connection supports them. Keep each durable preview and edit under the same outbox intent and use the committed turn result to finalize it. In eligible bot chats, send single-choice polls for clarification, scope votes to the original poll and actor, and use scoped text for approvals and for a definite poll refusal. Support standalone polls and native location pins, and receive shared or live locations. Support quoted media, media-only messages, voice-note transcription and native voice-note output in the supported audio format. [Hermes linked-device formatting and delivery](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/whatsapp.md#message-formatting--delivery)

**Send receipts.** Persist a message key before any operation for which the transport permits a reserved exact key. Associate returned keys with the corresponding leased attempt. Verify which linked-device evidence establishes platform acceptance. A successful pipe write or bridge process response alone does not establish it. Record verified server acknowledgements and delivered, read, played or error observations against the exact message key. Group receipts can apply to a single participant. A delayed status for that participant does not establish delivery to the rest of the group. A lost response after dispatch holds the attempt unless exact platform evidence settles whether it was accepted. [Hermes linked-device receipt fixtures](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/scripts/whatsapp-bridge/delivery_status.test.mjs)

## Business Cloud API adapter

**Account and service setup.** Register `whatsapp_cloud` from `hermes-whatsapp-plugin` as the separate Cloud factory. Use the native Rust HTTP client and a supported pinned Graph API version verified by the Cloud gate. The profile owner configures the Meta app ID, WhatsApp Business Account (WABA) ID, business phone number ID, scoped access token, webhook verify token, and App Secret. Verify the token's access and that the phone number belongs to the configured WABA through read-only Graph requests. Use a dedicated public HTTPS receiver with private owner operations on the existing native gateway boundary. Hold a lease for the receiver and a separate lease for every active verified business phone-number binding. Share the receiver across configured bindings only. Surface ready, not subscribed, invalid token, revoked, and misrouted registration states with redacted diagnostics. [Hermes Cloud setup guide](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/whatsapp-cloud.md) · [Meta Cloud API overview](https://developers.facebook.com/documentation/business-messaging/whatsapp/overview)

**Signed push intake.** Accept the GET challenge only for the expected subscription mode and verify token. For POST, authenticate `X-Hub-Signature-256` with the configured App Secret over the raw, size-bounded body before parsing. Resolve each row by its authenticated WABA and `metadata.phone_number_id`. Process all relevant entries and changes, including messages and statuses in the same callback. Commit each row's receipt or durable refusal through its verified binding or receiver, then return success. Return a retryable response if a required commit fails and deduplicate previously committed rows on replay. Do slow media downloads, native session admission, and agent work after this acknowledgement boundary. Reject invalid signatures and malformed envelopes at the receiver. [Meta webhook verification](https://developers.facebook.com/docs/graph-api/webhooks/getting-started/) · [Meta message webhooks](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/reference/messages)

- Admit DMs under scoped user grants and pairing. Use stable `wamid` values for message identity within the verified business phone-number binding. Use verified account-scoped identity evidence for phone-based sender IDs and business-scoped user IDs (BSUIDs) from the configured Graph version. Accept an opaque BSUID for routing when that is the supported recipient identity. Retain the original delivery identity when refreshing a verified alias. An unexpected group, unknown account, system notice, outgoing status, or unsupported kind starts no turn. [Meta business-scoped user IDs](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-scoped-user-ids) · [Hermes Cloud adapter](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/whatsapp_cloud/adapter.py)
- Support quick-reply buttons for up to three choices and a list for larger clarification choices within platform limits. Bind interactive clarification, approval, and command confirmation outcomes to the native request. The free-text option opens a scoped follow-up for that same request. A definite unsupported interaction can use the authorized text plan. Enable optional typing and read signals for accepted incoming messages using their WAMID and the authenticated phone-number client. Cloud sends the committed final content as ordered messages. [Meta messages API](https://developers.facebook.com/documentation/business-messaging/whatsapp/reference/whatsapp-business-phone-number/message-api) · [Hermes Cloud interaction guide](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/whatsapp-cloud.md#interactive-ux)
- Resolve a media ID through the verified Graph client and fetch bytes from permitted provider origins under scoped credentials, type and size limits. Refetch expiring references by the original verified media ID where possible. For an outbound artifact, record a successful media upload and media ID separately from visible publication. Send native image, video, document and audio messages. Encode a voice-note reply as Ogg Opus when supported, with an ordinary audio attachment option for eligible routes. Honor rate limits at the affected app, phone or recipient scope. A successful Graph send response records acceptance and the returned WAMID. Signed `sent`, `delivered`, `read`, and `failed` statuses update the exact recorded part and recipient when available. A status whose identity cannot be matched stays unapplied. Ambiguous POST failures use the outbox's uncertain state. [Meta messages API](https://developers.facebook.com/documentation/business-messaging/whatsapp/reference/whatsapp-business-phone-number/message-api) · [Meta message webhooks](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/reference/messages)

**Customer-service window.** Persist the latest verified user-message timestamp for each eligible business-number and recipient pair. Advance it from authenticated user messages only and keep it monotonic through out-of-order events and restarts. The free-form 24-hour window uses that provider timestamp, including when a job was queued earlier. Recheck eligibility when claiming delivery and immediately before dispatch, including rate-limit retries. Outside the window, record a typed blocked delivery for ordinary replies, interactive prompts, media and proactive results. Preserve the committed native result and intended recipient. A later inbound message opens eligibility for new authorized sends. A provider re-engagement refusal such as Graph error `131047` produces the same closed-window outcome. Configure and verify applicable consent, business eligibility, and a direct human escalation path for automated deployment. [Hermes Cloud conversation window](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/whatsapp-cloud.md#24-hour-conversation-window) · [WhatsApp Business Messaging Policy](https://business.whatsapp.com/policy) · [WhatsApp Business Solution Terms](https://www.whatsapp.com/legal/business-solution-terms/)

## Local implementation

- A linked-device profile pins its expected account JID and selects `personal` or `bot` mode. Check the private enrollment QR, scan it from WhatsApp, and complete enrollment using the enrollment lease ID as the credential reference. Use Node.js 20 or newer. Native packages stage the bridge and lockfile-installed Baileys dependency alongside the owner. For a source build, install the pinned dependencies with `npm ci --ignore-scripts` in `crates/plugins/whatsapp/bridge`.
- A Cloud profile pins `app_id`, `waba_id`, and `phone_id` and enrolls a credential containing `access_token`, `app_secret`, and `verify_token`. Select one `receiver_owner` for the Meta app and expose its reported `webhook_path` on a public HTTPS proxy. Forward this route to the local gateway and keep the native owner operations private. The fixture client uses Graph API v27.0. [Meta Webhooks verification](https://developers.facebook.com/docs/graph-api/webhooks/getting-started/)
- An unpaired DM sender can use `/pair` when the account enables direct pairing. The private owner can list exact pending requests with `messaging.profile.pending_pairings` and approve the selected code with `messaging.profile.pair`.

The live gates remain pending. Remaining linked-device work includes the provider's browser passkey ceremony, native standalone polls and location output, and editable progress previews. Further acceptance covers attachment quotations from confirmed outbound media and the dedicated Cloud free-text selection flow. [WhatsApp transport fixtures](../plugins/whatsapp/src/tests/)

## Scope

Exclude legacy Hermes bridge API and credential-file compatibility. The Cloud baseline covers DMs. Cloud group enablement, business template authoring and sending, and separate third-party agent products are outside these specs. Desktop UI work remains deferred.
