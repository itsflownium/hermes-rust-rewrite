# Gateway adapter contract v1

Mercury's gateway owns the lifetime of a channel conversation from the first authenticated event to the last recorded delivery. A stock messaging plugin is a separate Rust workspace crate with its own platform descriptor, configuration and connection factory. The gateway owns the shared adapter contract and registers bundled stock plugins. The native profile owner can enable each stock plugin independently.

The core polling and push conformance suite establishes the foundation. Expand and prove the [shared stock-plugin requirements](#shared-requirements-for-stock-plugins) before implementing any stock plugin. Each plugin passes its acceptance gate in the [messaging implementation order](../../BACKEND_PARITY_PLAN.md#messaging-implementation-order).

The contract covers the native Mercury host boundary. Hermes v0.23.4 supplies the reference behavior for the platform registry, normalized messages, session scoping, and delivery. [Hermes platform registry](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/gateway/platform_registry.py) · [Hermes message events](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/gateway/platforms/event.py) · [Hermes gateway behavior](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/developer-guide/gateway-internals.md)

## Existing code and target ownership

Mercury has one profile gateway owner, native session receipts, and a writer that commits turn history with execution authority. The messaging module already proves the adapter lifecycle, durable intake, native controls and the shared delivery outbox with synthetic transports. Routines and signed webhooks publish through that outbox. The current Telegram host has a separate poller and inbox. Telegram's adoption includes a one-time native data cutover onto the shared path. [Messaging runtime](src/messaging/runtime.rs) · [Core conformance](src/messaging/conformance.rs) · [Gateway authority](src/authority.rs) · [Telegram cutover](TELEGRAM_ADAPTER_SPEC.md#native-telegram-cutover)

| Owner | Responsibility |
| --- | --- |
| Profile gateway | Adapter registry and connection leases, verified profile binding, policy and capability checks, conversation routing, durable ingress and checkpoints, and the delivery outbox. |
| Native session authority | Queue order, execution claims and generations, interactive controls, approval and clarification state, committed history and receipts, and recovery of uncertain execution. |
| Adapter | Platform credential verification, network lifecycle, conversion of platform events and identities, formatting and delivery limits, and evidence from platform requests. |
| Engine | Provider and tool execution under the settings and permissions supplied by the gateway. |

Put the registry, ingress processing, and outbound coordinator behind a messaging module in `hermes-gateway`. Adapters call a connection-scoped ingress interface. The messaging module uses internal session admission and control methods and publishes results from committed receipts. Routines and webhooks submit outbound intents through the same coordinator. Store messaging records in the owning profile's `mercury.db`, using the existing profile database and conversation writer. Adapters use scoped host operations for staging attachments and reading reply artifacts. [Profile database](../engine/src/db.rs) · [Attachment handling](src/upload.rs)

## Interface

The gateway validates contract major version, adapter identity, configuration, and advertised capabilities before activating a connection. Version 1 requires text intake and text delivery for message adapters. The stock-plugin extension also negotiates an internal wake-only adapter, with no message send capability. Negotiate additional capabilities per connection and apply the authorized destination's capabilities before preparing an effect. These include topics or threads, command and prompt interactions, streaming media and audio, and platform display operations. A capability request without support produces a typed refusal, with any supported fallback chosen by gateway policy.

| Operation | Contract |
| --- | --- |
| Register and connect | An adapter supplies its platform identifier, version, capabilities, and connection factory. The gateway binds the configured adapter to one profile, verifies the platform account, and grants a connection lease. The adapter reports readiness, retryable disconnects, or a configuration or credential failure. |
| Stage a transport handoff | When the transport can persist its own receive position before event admission, the adapter durably stages a bounded, scoped handoff that can finish processing after restart. The gateway controls the position used for subsequent intake. |
| Submit an event | The adapter presents an authenticated platform event, its replay identity, and an optional resume checkpoint. A durable result identifies acceptance, a repeat of a prior result, refusal, or conflicting reuse, and returns the stored checkpoint when one is in use. A failed commit is an explicit request to retry or resume from the last durable checkpoint. |
| Stage a wake | A negotiated wake adapter submits a typed, authenticated trigger for its configured owner session. The gateway durably accepts, deduplicates and schedules the wake under native authority. Native message delivery is unavailable through that adapter. |
| Prepare a delivery | The gateway supplies a committed, authorized intent. The adapter returns an ordered, bounded plan of platform operations without performing network effects. The gateway records the plan and stable part identities before the first attempt. |
| Send a part | The adapter performs one platform operation for one leased attempt and returns classified evidence for the effect and its individual recipients where the platform reports them. The gateway records the result and uses it to decide whether and when another attempt can start. |
| Report a delivery update | An adapter that observes asynchronous delivery status submits authenticated evidence for the exact account, platform effect, and recipient when supplied. The gateway durably deduplicates the update and applies it to a verified attempt when it can establish the association. |
| Stop or reconnect | The gateway stops new intake and delivery claims, drains or cancels in-flight operations, and revokes the connection generation. A new connection uses the persisted checkpoint, active routes, and receipts. Stale connection generations cannot admit updates or settle attempts. |

Expose health and receipt status through the native profile owner, with the relevant profile, connection, conversation, and attempt identifiers. Credential values and message bodies stay out of operational status and diagnostics.

## Identity and policy

The gateway assigns the profile and connection scope after verifying the external account. It grants one active intake lease per platform account within a Mercury installation. When a receiver serves multiple accounts, the owner also leases that receiver. Bind each incoming event to exactly one verified account before admitting it. Platform IDs are opaque values. Labels, usernames, and message-supplied profile names have no authority.

A transport can scope its state and recovery guarantees to a device or session within the verified account. Record that scope separately from account and route identity. Renew credentials in place only with proof that the scope survives. On scope replacement, preserve native receipts and valid account bindings. Restore device-scoped state and replay authority only for the verified scope that created them.

An authenticated receiver identifies the service and app. Bind each item to the installation and resource whose current grants cover that operation, then verify the actor and route separately. Preserve which resource authorized the capability and fence it when uninstall, membership loss or consent revocation invalidates it. Check the gateway's admission, protected-read and publication grants independently of the provider's receive grant.

The private profile owner can provision a transport credential interactively. Bind the short-lived setup lease and its sensitive artifacts to the owner and intended configuration. Verify the account before granting the active lease. Persist credential mutations under the setup or active generation that authorized them. Revocation fences the previous generation, including writes to credentials. Transport enrollment and sender DM pairing use separate grants.

An inbound event carries a verified chat and optional subdestination, sender and relevant membership evidence, and an event ID within the platform's replay scope. It carries normalized content or a typed control action. The gateway records two identities. The conversation binding selects the native session from the owning profile, verified account, chat, thread or topic, and policy-selected participant scope. The delivery destination records the exact original chat, subdestination kind and ID, and reply anchor when applicable. Sharing a conversation across destinations preserves each input's delivery destination and the session's turn order. Use a deterministic creation key to recover a session created before an interrupted route write. A lost mapped session is blocked pending an explicit owner decision.

When dispatch depends on a provider-issued address or temporary handle, retain it separately from the stable logical destination. Bind its evidence to the verified account, installation, exact resource, operation and expiry when supplied. Refresh it only with proof of the same authorized binding. A send attempt retains the address it used for exact reconciliation. Check the required credential audience and verified network origin for each use. A change of endpoint, token audience, or redirect requires verified authority for that request.

A platform can identify the same actor or destination through more than one opaque identifier. Record a verified association with its evidence and scope it to the profile, account and identifier namespaces. Use it for policy, logical input identity and conversation binding while retaining original transport keys and immutable receipts. A display label or presented phone number grants no association. A conflicting or reassigned identity requires owner resolution. An automated echo must carry verified provenance or match a durable outbound identity. When an adapter admits owner-authored messages from the same account that it uses to send, resolve that authorship before native intake or controls.

Room policy determines whether a participant can submit work, whether a room shares its session, and which mentions, commands, tools, and controls are allowed. Recheck the current connection and applicable policy at intake, before claiming a turn or executing a control, and before each external delivery attempt. A credential change to another platform account creates a new connection identity. Pending work continues to refer to its original identity and destination. A platform can withdraw trust in an external account or recipient independently of Mercury policy. Record a scoped refusal and require renewed transport evidence before proceeding under the original binding. Room classification, directory aliases and display metadata provide context. Admission and any audience change require the applicable binding and current grants. Resolve configured turn-local prompts for the authorized route at native claim. Keep that prompt material out of the durable transcript and other routes that share the session.

An effect can also require transport eligibility that expires. Check it before claiming a delivery and again immediately before dispatch, across restarts and retries. Derive expiry from authenticated provider or native receipt timestamps and the operation's rules. A replay or status update does not extend it. A blocked delivery retains its committed intent, original destination and typed reason. New eligibility applies to newly authorized work.

Record the transport protection required for the authorized destination. Verify that protection and its audience before staging protected data and before dispatch or retransmission. A lost protection capability or changed audience holds the affected work. Resume through the original protected binding only with renewed evidence. Keep cryptographic key material and decrypted content inside their authorized profile boundaries.

Approval and clarification prompts carry gateway-issued action identities bound to the intended actor or role, conversation, pending request, and execution generation. Repeated and stale responses return their recorded decision or a typed refusal. Queue edits, steering, redirects, interruption, and prompt responses all use the same native authority as local clients. Media and remote text pass through the gateway's data and attachment policy before use by the engine.

A provider callback can require an immediate rendered result. Derive it from the committed native decision under current actor and audience authorization. A lost response or stale presentation never causes another native decision. Track any subsequent visible update to the original prompt as an independently authorized effect with its own receipt.

## Intake, ordering, and execution recovery

1. Authenticate the transport and normalize the event. Record the policy revision and the minimal evidence needed to identify and replay its disposition.
2. Commit the accepted input or durable refusal, along with any safe cursor advancement. Advance a batch checkpoint only through the durably handled prefix. Polling and push adapters follow their platform's acknowledgement and resume rules. When a push envelope spans several accounts, route and commit each item under its verified account or record a receiver-scoped refusal for an unroutable item. Acknowledge the envelope only after all required dispositions commit. After partial failure, retry the envelope and read the previously committed dispositions.
3. Persist the transport event receipt and derive native submission identity from the verified connection and logical input. When distinct platform events describe one logical input, record their identities as aliases of the same native receipt. An edit or control carries its own operation identity and references its target. Resolve or create the routed session within the owning profile. A repeated event identity with equal immutable data reads the original disposition. Bind refreshable authorization evidence, transport credentials and derived context separately from the replay fingerprint. Conflicting reuse preserves the original and returns a conflict.
4. Claim the queued turn under the current owner and policy. Persist the claim before starting the engine. Use the native turn boundary to commit history and the terminal result together.

Use the earliest handoff the adapter controls when the protocol library acknowledges independently. Keep each replayable handoff until its host receipt commits. Report an observed gap if intake cannot be recovered. The adapter's transport acknowledgement does not substitute for a host receipt. When a library commits its receive or crypto position before returning normalized events, retain the recoverable source and sufficient processing evidence before that commit. The host can finish every unsettled disposition from the handoff even if the library treats the batch as already seen.

Keep transport resume checkpoints separate from durable logical input identities. Scope a checkpoint to the verified account and the provider's replay scope. Report connection readiness separately from intake continuity. From the replay evidence, report verified recovery, an observed gap, or an interval whose continuity remains unverified. When the replay scope ends or the provider can supply only a bounded suffix, preserve prior dispositions, then process eligible recovered and live events using their logical identities.

An adapter with an authorized history recovery path can repair an observed gap within a bounded interval and resource scope. Persist the repair progress and stage live arrivals for the affected route. Merge recovered and live inputs by their durable logical identities and established source order. Release the route after repair or a durable disposition for the remaining gap. Context-only history and initial activation baselines do not admit historical work.

Persist a deferred input under its original identity when verified content or a required related event is still pending. Scope the recovery evidence and expiry to the verified actor, destination, and receipt. A later event can complete preparation once under current policy. Before that point, do not claim native work or fetch media that depends on the missing authorization. Expiry or permanent inability to establish the required evidence becomes a durable disposition. The affected route observes input order while other routes can continue.

The route orders ordinary inputs and replies. Authorized controls for a running turn can reach the authority while that turn is awaiting an answer. An uncertain execution fences further ordinary turns in its route until the owning authority resolves it. Other routes remain eligible for work. A restart reconciles durable intake, queued receipts, and committed results. A claim with an uncertain execution outcome enters the existing native unknown-resolution path. Retain deduplication identities through the adapter's supported replay window and for all unsettled work.

## Delivery and recovery

A reply intent references a committed turn result or a durable, authorized producer notification. The intent records the approved destination, any conversational reply anchor, and stable delivery identity. The gateway validates the rendered plan against the authorized destination and records each part with its own durable attempt and platform receipt. Parts for the same destination are sent in order. Negotiated display operations can track progress, stream previews, or update an existing platform message under the authorization of the same intent. The committed outcome determines the final reply. Expiring transport signals such as typing and native drafts carry no receipt for a durable message and do not hold destination order. A display operation that can create or mutate a durable message uses the same attempt and uncertainty rules as any other durable effect.

| Result | Gateway action |
| --- | --- |
| Confirmed | Commit the platform receipt as confirmed acceptance, then release the part's order fence. A restarted owner resumes from the next unfinished part. |
| Submitted to a write-only connection | If the profile authorizes this negotiated delivery level, commit a complete write as a terminal submission without claiming remote acceptance. Release the part's order fence. A partial or interrupted write is uncertain. |
| Partially accepted | Persist evidence for each reported recipient. A complete, terminal partial outcome releases the part's order fence. Uncertain recipients keep the destination fenced until the applicable attempt settles. |
| Retryable with evidence of non-acceptance | Persist the retry deadline and its scope. Retry the same part after that deadline under current policy. An explicit platform rate limit is one such result. |
| Blocked before dispatch | Record the transport eligibility refusal and keep the committed intent and original destination. |
| Definitively rejected | Record the terminal failure and make it visible to the operator. |
| Uncertain | Hold the part and later deliveries to its destination while it awaits exact evidence, a qualified retransmission or owner resolution. A missing response, ambiguous transport failure, or interrupted send claim enters this state. |

Persist each attempt before invoking the adapter and associate any safely reserved platform operation key with that attempt before dispatch. On restart, reconcile incomplete attempts while holding the new owner lease. Positive platform evidence may confirm acceptance. A configured owner can also mark the exact attempt delivered or discard it. For an unsettled send, only confirmed non-acceptance permits a new automatic attempt that could create a second effect. Resolving one attempt releases its destination's order fence and leaves other destinations independent.

A platform can report mixed outcomes within one authorized destination. A retry may cover only recipients with confirmed non-acceptance and requires a supported operation that preserves the original destination and authorization. A full-destination retry requires confirmed non-acceptance for the entire effect. Record accepted recipients even while other recipients remain held. A later receipt can settle the exact recipient without confirming the rest.

A protocol-guaranteed, deduplicated retransmission can settle the same attempt after an ambiguous response. Record the transmission key, qualified guarantee and original effect scope before dispatch. Require the same provider-defined device or session, endpoint, destination and immutable prepared request, current delivery authority and protection, and a still-valid deduplication horizon. Retransmission uses the original effect identity under the current lease. If any condition is unproven, reconcile with read-only evidence or keep the existing uncertainty. A correlation identifier alone gives no permission to retransmit. A short server cache is evidence only while its applicability and continuity are verified. Expiry, eviction or a server change can invalidate it.

Store accepted, delivered, read, played, and failed evidence according to the adapter's supported stages. Deduplicate status updates and preserve verified progress on out-of-order or conflicting observations. Some statuses describe one recipient of a group effect. Associate each update only with an exact recorded attempt and its verified account, destination and platform effect identity. A status can arrive before the send receipt. Keep it unapplied until exact association is possible. A stage that establishes acceptance may settle the matching uncertain attempt. A subsequent delivery failure remains visible on the accepted receipt and does not reopen that send. An authenticated observation of the gateway's own effect can establish acceptance after a lost response when the provider evidence links its exact effect identity and verified author and destination to the recorded attempt. It can do so after the retransmission window closes.

Track durable presentation markers under their exact intent, target and confirmed platform identity. The gateway can authorize retirement of its own marker after completion, cancellation or revocation of the invoking actor's grant. Cleanup requires the current connection and platform permissions and can only remove or retire the recorded marker within its existing audience. Adding content or a new marker requires current authority for publication. Record whether the effect can notify the wider audience. Keep automated previews, progress and edits quiet by default. Resolve any deliberate mention or wider notification against current policy and the exact audience.

## Adoption and completion

1. **Spec each stock plugin individually.** Compare its supported workflows with the existing specs. Add common host behavior and its conformance case to this contract as overlap is found. Keep platform-specific protocol and presentation decisions in that plugin's spec.
2. **Complete the shared implementation gate.** Preserve the core polling and push suite below. Implement the shared stock-plugin requirements and verify every row through the real gateway owner. Run the conformance suites and `cargo test --locked --workspace` before starting a production plugin.
3. **Adopt and accept one plugin at a time.** Use the tested gateway for routing, checkpoints, commands, admission and delivery. Where Mercury already persists platform state, migrate once under the current owner and account locks. Preserve valid configuration, inbox history and acknowledgement position. Historical rows stay visible without enqueuing turns. The shared host is the sole live writer at cutover. Complete each plugin's transport and live gates before starting the next.
