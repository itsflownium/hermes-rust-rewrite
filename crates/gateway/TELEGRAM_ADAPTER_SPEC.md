# Telegram stock plugin implementation spec

Telegram is the second stock messaging plugin. Local implementation and fixture testing can proceed while Discord's live acceptance is pending. Release integration follows the shared gateway and Discord acceptance gates. Telegram's integration and live acceptance come before [Slack](SLACK_ADAPTER_SPEC.md). The reference is the bundled Telegram platform in Hermes v0.23.4 and Telegram's current Bot API. [Shared gateway contract](ADAPTER_CONTRACT.md) · [Discord spec](DISCORD_ADAPTER_SPEC.md) · [Hermes Telegram guide](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/telegram.md) · [Telegram Bot API](https://core.telegram.org/bots/api)

## Target architecture

Register the separate `hermes-telegram-plugin` crate with platform key `telegram`. Reuse the Bot API transport in `hermes-telegram` for verified identity, requests and protocol errors. Return each update's identity with its normalized input or a typed refusal so the shared intake can commit the safe prefix. The Telegram adapter implements polling and webhook intake, Bot API rendering, media transfer and platform receipts. The native owner manages its configuration, credentials, lease, authorization, conversation bindings, native command effects and outbox through the shared contract. [Telegram plugin](../plugins/telegram/) · [Current Bot API client](../telegram/src/telegram.rs) · [Gateway adapter interface](src/messaging/types.rs) · [Hermes platform manifest](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/telegram/plugin.yaml)

Use the shared setup and receipt APIs for profile configuration, authorized manual replies, scheduled and signed webhook results, and background work. Bind the account to the numeric bot ID from `getMe`. Validate the new token against that identity on rotation. Expose the selected intake mode, verified bot, poll or webhook health, send health, supported topic and inline capabilities, and recovery or rate-limit status in the private owner. The platform can report denied capabilities when BotFather settings, privacy mode, or chat membership limit visibility. [Telegram getMe](https://core.telegram.org/bots/api#getme) · [Telegram bot privacy mode](https://core.telegram.org/bots/features#privacy-mode)

## Access and conversation routing

- Use signed numeric Telegram chat IDs and numeric actor IDs. Scope direct user grants, group-only user grants, room and topic grants, verified operator membership, and pairing to the profile and bot. Match display labels only for navigation. Apply exact topic settings before parent settings and honor explicit denials. A group membership grant authorizes work in that group. Native controls and administrator commands require their own actor and permission checks. [Hermes group allowlisting](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/telegram.md#group-allowlisting)
- In groups and supergroups, support bot-addressed mentions, replies and configured wake patterns, mention-free rooms, and an explicit opt-in for guest group mentions. The guest exception requires a fresh direct mention on each turn. Broadcast channels require explicit room authorization. Resolve mentions and reply authors from Telegram's entities and verified bot identity. Give an explicit mention of another bot precedence over general wake triggers. Support opt-in observation of authorized group context without starting turns, and retain the authors and source of that context so the engine can distinguish it from addressed instructions. [Hermes Telegram addressing](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/telegram/telegram_addressing.py) · [Hermes observed group context](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/telegram/telegram_group_observe.py)
- A forum topic or private-chat thread has its own destination. Support independent sessions by topic, room-policy selection of shared versus per-participant group sessions, and the private DM mode in which ordinary threads share one conversation while each reply returns to its original thread. Preserve exact topic or parent model, prompt, skill, tool, and approval settings. Keep Telegram's `message_thread_id` and `direct_messages_topic_id` as distinct destination kinds. Edits and reactions target a confirmed message in its actual chat. [Hermes topic routing](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/telegram/telegram_topic_routing.py) · [Telegram message model](https://core.telegram.org/bots/api#message)
- Support configured private topics as well as user-managed `/topic` mode. Check the bot's threaded-mode and topic-creation capabilities on activation. Persist topic creation and naming through the shared provisioning path, with binds for explicitly restored sessions limited to the same profile, bot and authorized user. Support the root lobby, last-active-topic continuation and opt-in fresh topic creation under the chosen policy. Commit the destination selection before native admission. A known vanished topic is a blocked route and can be restored through a scoped owner operation. [Hermes private topics and multi-session mode](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/telegram.md#private-chat-topics-bot-api-94) · [Telegram topic support](https://core.telegram.org/bots/features#topics-in-private-chats)

## Intake and recovery

**Long polling.** Load the bot's saved next offset. Process the returned batch in update order and commit dispositions for the safely handled prefix. Only a later `getUpdates` call with a higher offset acknowledges those updates to Telegram. Durable media and topic preparation can continue after the commit. A restart or failed commit resumes from the last saved offset. Preserve the ordinary cold-boot backlog. Support an explicit owner-selected discard on a cold boot with a recorded gap. Reconnects, rate limits and poller conflicts preserve queued updates. Treat successful polling and successful sending as separate health signals. [Telegram getUpdates](https://core.telegram.org/bots/api#getupdates) · [Hermes polling recovery](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/telegram/adapter.py#L1935)

**Webhook intake.** Under the same account lease, support an exclusive push mode using `setWebhook` and a per-connection secret token. The native owner binds a dedicated webhook path to the verified bot and validates `X-Telegram-Bot-Api-Secret-Token` before parsing the bounded request. A public HTTPS reverse proxy can route that endpoint while private owner operations remain on the private service. Return success after a committed disposition. A known storage failure returns a retryable HTTP response. Run callbacks and Bot API sends as separate recorded effects so an HTTP response to an update never stands in for a delivery receipt. Change mode under the account lease after draining intake and verify the new registration while keeping Telegram's backlog. [Telegram setWebhook](https://core.telegram.org/bots/api#setwebhook) · [Telegram webhook response limits](https://core.telegram.org/bots/api#making-requests-when-getting-updates)

**Replay and ordering.** Scope each `update_id` to the verified bot and a valid Telegram update epoch. Retain exact replay identities across both intake modes for the Bot API's replay window and for unsettled work. Separate checkpoints from deduplication so an out-of-order webhook does not discard a distinct preceding update. Normalize and commit edited messages by their own update identity. Apply queued-input edits to the native admission identified by the original message when authorized. Handle Telegram's idle sequence reset with an explicit checkpoint transition. Report known retention gaps and uncertain execution through the shared owner. Execute ordinary work in the host's committed route order. [Telegram Update](https://core.telegram.org/bots/api#update) · [Hermes repeated update handling](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/telegram.md#repeated-inbound-updates)

**Preparation.** Albums and compatible message bursts can form one native input. Persist every constituent update ID and the grouping decision before acknowledgment. Group by verified account, actor and exact destination. Retain captions, file identity and attachment order. Recheck access before downloads, contextual reads, transcription, or native admission. A claimed uncertain execution stays fenced in the shared native authority even if Telegram resends the update. [Hermes media albums](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/telegram/telegram_album.py) · [Hermes input batching](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/telegram/telegram_batching.py)

## Commands and controls

Render the native command and skill catalog into scoped `setMyCommands` menus with deterministic priorities and a cap within Telegram's 100-command limit. Offer `/commands` and the authorized, paginated inline picker for eligible commands beyond the menu. Reauthorize a selected command when it arrives in a conversation. Support `/model` with a direct argument or a provider and model picker, native session and busy-turn controls, `/sethome`, `/topic`, and voice reply settings. Use the private owner for actions that change profile-wide policy. [Hermes Telegram command discovery](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/telegram.md#command-menu-priority-and-cap-optional) · [Telegram command scopes](https://core.telegram.org/bots/api#botcommandscope)

Use inline buttons for approvals and clarification choices and accept a typed reply where configured for the active request. A button carries a compact host-issued reference within Telegram's 64-byte callback payload limit. Bind it to the bot, originated message, chat and topic, actor or permitted operator, request, expiration, and execution generation. Call `answerCallbackQuery` promptly after its durable admission or refusal, and show the native result or retire the underlying card as appropriate. A duplicate or stale tap can read a scoped outcome without rerunning the control. When a card is definitively undeliverable, a policy-approved plain prompt can reuse the same native request. Uncertain presentation retains the original delivery fence. [Telegram callback query](https://core.telegram.org/bots/api#callbackquery) · [Hermes Telegram clarification binding](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/telegram/telegram_clarify_binding.py)

## Delivery and media

**Exact destinations.** Resolve a home, thread, private topic, or a permitted channel for each producer. Register a verified destination before it has a session when needed. All sends and follow-ups use that destination and the original reply reference where applicable. Thread deletion, an unknown topic ID, or lost membership produces a typed failure or fence on that destination. Telegram's general forum topic uses Telegram's documented wire representation of that same destination. A verified supergroup migration can be handled as a scoped owner-approved destination transfer with the original receipts preserved. [Telegram forum topic methods](https://core.telegram.org/bots/api#createforumtopic) · [Telegram response parameters](https://core.telegram.org/bots/api#responseparameters) · [Hermes home and cron topics](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/telegram.md#home-channel)

**Formatting and status.** Render Telegram message entities, links, captions, code and reply parameters with bounded, Unicode-safe splits. Use native drafts for capable private chats and topics and opt-in Rich Messages for supported content. Elsewhere use ordinary formatted messages and the negotiated status operations. Keep final replies durable, edit confirmed status messages in place and make typing, intermediate progress and optional reactions quiet. Gate inline button retirement, reactions and optional pinning on the bot's current permissions. Treat a draft as expiring presentation tied to the turn. An opt-in bot status description can reflect connection and graceful shutdown under the verified account lease. The final reply is a committed outbox effect. [Telegram formatting](https://core.telegram.org/bots/api#formatting-options) · [Telegram drafts](https://core.telegram.org/bots/api#sendmessagedraft) · [Telegram Rich Messages](https://core.telegram.org/bots/api#sendrichmessage)

**Delivery evidence.** Record Telegram's returned message IDs against the leased parts. Persist confirmed non-acceptance and `retry_after` in the shared cooldown. Use the proven chat or method scope when available and an account cooldown when the scope is uncertain. Independent destinations remain eligible outside that scope. Use the confirmed ID for a later edit. A missing response to a send or topic creation is an uncertain effect until exact platform evidence or owner resolution settles it. Alternative rendering or a reply without an anchor can be planned after a definite refusal and only within the same approved destination. [Telegram responses](https://core.telegram.org/bots/api#making-requests) · [Hermes Telegram flood cooldown](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/telegram/telegram_flood_cooldown.py)

**Files and inputs.** Accept photos and albums, video, audio, voice notes, documents, animations, stickers, contacts, and locations under the shared data policy. Preserve captions and source attribution. Represent contact cards and static locations as structured context. Coalesce live location updates with bounded movement and time criteria in the same share. Use scoped vision analysis for supported static stickers and preserve their supplied emoji and label as an available fallback. Feed voice notes to the profile transcription service or deliver the scoped audio artifact for authorized tool inspection. Generate spoken replies with the profile synthesis service and send the result as Telegram voice or audio. Deliver other generated artifacts via the host's reply artifact API. [Hermes Telegram media and locations](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/telegram.md#shared-contacts-and-locations) · [Hermes live location handling](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/telegram/telegram_live_location.py)

**Deployment options.** Support explicit Bot API and file origins, profile proxy settings, and the self-hosted Bot API server for larger files. Keep token-bearing request details out of diagnostics. Stream file data within the smaller of platform and host bounds. In local-server file mode, read only from an operator-configured shared root with canonical path and file checks, then stage through the same host attachment path. Cover switched origins, incompatible file references, upload limits and cleanup in transport fixtures. [Hermes proxy and local Bot API settings](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/telegram.md#large-files-20mb-via-local-bot-api-server) · [Telegram local Bot API server](https://core.telegram.org/bots/api#using-a-local-bot-api-server)

## Native Telegram cutover

The existing Mercury installation stores Telegram setup in `messaging/telegram/settings.json`. Early versions used `bot-<id>.inbox.json` for the bot identity, next polling offset, and messages. Current versions import that inbox into `mercury.db` and also store routes, update dispositions and pending delivery attempts there. The existing Telegram profile host and Messaging view use that store. Migrate these user records once when adopting the shared write path. [Telegram store](../telegram/src/store.rs) · [Telegram SQLite inbox](../telegram/src/store/inbox.rs) · [Telegram host](src/telegram_host.rs) · [Existing Messaging client](../desktop/src/messaging.rs)

1. Verify the configured token with `getMe` when available. Under the profile owner, acquire the shared account lease and the predecessor's `bot-<id>.connection.lock` before snapshotting the SQLite records or the earlier JSON inbox and settings. Report a busy predecessor as an ownership conflict. Retain verified historical inboxes under their own bot identities, including disabled setups. Resolve a missing or mismatched credential through the private setup operation before activation.
2. Prepare the new profile credential reference. Copy the verified bot binding, enabled state, user allowlist, inbox history, recorded sends and exact next offset. Import settled updates and outbound confirmations as historical receipts and leave their transcripts visible. Carry forward definite pending work and preserve existing fences for uncertain turns and sends.
3. Commit the imported metadata, history and checkpoint under an idempotent migration receipt scoped to the bot, source version, and profile. A restart before commit can safely repeat the import. A restart after commit reads the new records and continues from their saved offset. Unreadable source data remains available for owner recovery without dropping the queued updates.
4. Move the existing setup, status, inbox read, and manual reply callers to the shared owner before enabling stock Telegram traffic. Keep the migrated input files as a read-only recovery copy. Remove the predecessor's runtime, live JSON writer and direct send call sites from the shipped path. The shared host owns all new admissions and delivery effects.

## Implementation and acceptance

The stock crate can be enrolled through the native owner for a bot without predecessor data. Setup pins the numeric bot ID. A bot with saved predecessor state requires migration before the stock adapter starts its transport. Both runtimes use the predecessor's per-bot lease while the cutover is pending.

Local fixtures exercise the polling checkpoint, authenticated webhook intake and mode changes, duplicate and conflicting updates, uncertain sends across restart, exact DM and topic replies, clarification controls, album recovery, voice notes in both directions, and an owner notification to a verified destination. The remaining acceptance work includes the saved-profile cutover, topic provisioning and session restoration, guest and observed group context, the command pickers, and live bot workflows.

| Bot setup and intake | Shared stock-plugin gate and Discord live acceptance | Normal profile startup verifies the account. Polling and webhook fixtures commit replies and preserve the offset and dedup identities across restart and mode change. |
| Scope, topic sessions and commands | Verified intake and the shared route and command APIs | DMs, groups, group forum topics and private topics exercise their permissions, model and skill rules, restoration, and native prompt controls. |
| Rendering, notifications and media | Authorized routes and shared delivery and audio APIs | Exact-destination text, drafts, status edits, files, voice, and producer results use the same outbox receipts. |
| Cutover and live acceptance | Full transport integration | The locked one-time importer passes restart cases on both sides of its commit, the predecessor host is retired, and a configured bot passes the live workflow matrix. |

## Scope exclusions

- Hermes configuration and database compatibility, deprecated mixed user and chat allowlist fields, legacy edit-only streaming fallback and old Bot API parameter aliases.
- Standalone Mercury Telegram runtime, third-party hosted connectors, and Desktop UI work.
